# Changelog

## 1.14.0 (unreleased)

Earlier release notes are on the [GitHub releases page](https://github.com/absmartly/javascript-sdk/releases); the [Migration Guide](README.md#migration-guide-113x--1140) lists the other changes in 1.14.0.

### Added

- Switchback experiments (R33, cluster-defined): an experiment with `randomizationType: "switchback"` is served by cluster and period through the existing `treatment()`, `peek()`, `variableValue()` and `peekVariableValue()`, matching the collector and java-sdk. `ExperimentData` gains the optional `randomizationType`, `switchbackClusters`, `switchbackClusterValues`, `switchbackStartAt`, `switchbackPeriodMs`, `switchbackCarryoverDurationMs`, `switchbackBurnInDurationMs`, `switchbackBurnOutDurationMs`, `switchbackDesignType` and `switchbackEstimand` fields. There is no new method or option. See [Switchback Experiments](README.md#switchback-experiments).
- Known limitation: JavaScript cannot tell `3.0` from `3`, so a cluster attribute set to an integral float is keyed like the integer (`"3"`), where other SDKs give a float no cluster value. A cluster map with two or more linked unit types, one named like an array index (`"1"`), cannot keep its declared order in JavaScript, so it is served as an ineligible control (variant 0, no exposure).

### Changed

- Shared variable keys pick and expose one experiment, as the Java SDK does. Before, `variableValue()` exposed every experiment it checked that had the key, including ones the unit was not in (for example a strict audience mismatch or a switchback that gives way), which recorded users in experiments they never saw; and when the first experiment's selected variant lacked the key, a later experiment's value was served and exposed, so which experiment a unit was counted in depended on its arm, biasing the result. Now candidates are the experiments defining the key in any variant, by experiment id ascending; the winner is the first one the unit is in (assigned, overridden or rule-assigned), whatever its arm, and returns its variant's value (`null`, `false`, `0` and `""` included) or the caller default if that variant lacks the key. With no winner, a held-out candidate supplies its control value, otherwise the caller default. Only the winner is exposed (an out-of-range overridden, custom or full-on winner is exposed with that variant; a silent switchback winner, before its schedule starts or with an ineligible cluster, returns control and records nothing); each checked candidate's applicable holdouts still fire, as in Java. `peekVariableValue()` exposes nothing. Keys no experiment defines return the default, including names like `toString` or `__proto__`; a variant config that defines such a key (`toString`, `constructor`, `__proto__`) no longer fails the context. Who moves: anyone with two or more running experiments sharing a variable key, and anyone counting exposures from `variableValue()` on an experiment the unit is not in (use `treatment()` to record those).
- Switchback experiments that are already running change assignment for this SDK: before, they were served as a sticky unit assignment on their `unitType` (or not at all), which did not follow the switchback schedule. Now, once an override, assignment rule, strict audience, full-on setting or traffic check has not decided the variant, each unit gets its cluster's scheduled variant for the current period, and exposures are recorded once per period under the serving unit, while that period's assignment stays cached. Who moves: customers who run switchback experiments. The switchback support itself does not change unit experiments or context data without switchbacks; the separate shared-variable-key fix above can change their variable reads.
